# Application Quality Evaluation Report

## 1. Overview

This document describes the application-level quality evaluation workflow for the **End-to-End LLMOps Project**, including the metrics, initial results, interpretation, limitations, and recommended next steps.

**Evaluation status:** The evaluation script completed successfully, evaluated all three test cases, and generated a JSON report. All three cases passed the configured metric thresholds. These results are an initial baseline, not a final benchmark.

## 2. What Is Being Evaluated?

Application-level evaluation assesses the quality of answers generated by the complete Retrieval-Augmented Generation (RAG) application. It considers generated-answer correctness, completeness, writing quality, relevance, and support from retrieved context.

### Components involved

- **Evaluation dataset:** `evaluation/datasets/application_quality_eval.json`
- **RAG application:** `ConversationalRAG`
- **Embedding model:** `sentence-transformers/all-MiniLM-L6-v2`
- **Vector store:** FAISS
- **Retrieval strategy:** Maximum Marginal Relevance (MMR)
- **Retriever settings:** `k=3`, `fetch_k=10`, `lambda_mult=0.5`
- **LLM judge:** Groq model `openai/gpt-oss-20b`, accessed through `DeepEvalGroqModel`
- **Evaluation library:** DeepEval
- **Evaluation script:** `evaluation/application/quality/evaluate_quality.py`
- **Output report:** `evaluation/reports/application_quality_results.json`
- **Score threshold:** `0.70`

The dataset currently contains three questions about Transformer architecture, self-attention, and multi-head attention.

## 3. Metrics Used

| Metric | What it measures | High score means |
|---|---|---|
| Correctness | Factual correctness compared with the expected answer | The answer is accurate |
| Completeness | Coverage of essential information | Important concepts are covered |
| Style | Clarity, readability, organization, grammar, tone, and conciseness | The answer is clear and well written |
| Answer relevancy | Whether the answer addresses the question | The answer stays on topic |
| Faithfulness | Whether the answer is supported by retrieved context | The answer is grounded in retrieved evidence |
| Hallucination / groundedness | Custom GEval check for unsupported or contradicted factual claims | The answer is well supported by context |

### Important note about the custom groundedness metric

The report retains the metric key `hallucination` for compatibility with existing report consumers. However, the custom GEval criteria are **positive-oriented**: a high score means the answer is well grounded, while a low score means the answer contains unsupported or contradicted claims. Interpret this score as a **groundedness score**, not as a measure where a higher score means more hallucination.

## 4. Evaluation Workflow

1. **Load the evaluation dataset** from `application_quality_eval.json`.
2. **Initialize the RAG application** using `ConversationalRAG`.
3. **Load the FAISS index** from `faiss_index/session_20261026_215230_88296173`.
4. **Configure retrieval** using MMR with `k=3`, `fetch_k=10`, and `lambda_mult=0.5`.
5. **Generate an answer** for each question.
6. **Collect retrieval context** for the evaluation test case.
7. **Evaluate the answer** with six DeepEval metrics using the Groq judge.
8. **Aggregate results** into per-metric averages, pass rates, and overall case statistics.
9. **Save the report** to `application_quality_results.json`.

## 6. What Is Working and What Needs Attention?

### Working

- The evaluation script completes and saves a JSON report.
- The RAG application, embedding model, and FAISS index load successfully.
- All six metrics return scores for all three test cases.
- GEval scoring instructions were updated to use a 0–10 scale, which DeepEval normalizes to a 0–1 score.
- The evaluation produced three passed cases, zero failed cases, and zero metric errors.
- Per-case outputs, retrieved context, scores, reasons, and durations are available in the JSON report.

### Needs attention

- **Small dataset:** Three questions are insufficient for a reliable quality benchmark.
- **Judge limitations:** LLM judges can make mistakes or produce inconsistent scores. Manually review sample answers, contexts, scores, and reasons.
- **Groq rate limits:** The run encountered HTTP `429 Too Many Requests` responses. Retries succeeded, but larger evaluations may need controlled concurrency and retry/backoff handling.
- **Grounding interpretation:** The custom metric is stored under the `hallucination` key but is scored as positive-oriented groundedness. Documentation and downstream dashboards should make this distinction clear.
- **Retrieval context consistency:** The script obtains context for evaluation by invoking the retriever separately from answer generation. Depending on the application chain, this may not exactly reproduce the context used internally during generation. For stronger faithfulness assessment, capture the actual context passed into the generation chain.
- **Reference quality:** Verify expected answers against the source document and ensure each answer defines clear acceptance criteria.

## 7. How to Improve the Evaluation

Make one change at a time and rerun the same dataset so results can be compared fairly.

### Step 1: Expand the dataset

Add more questions covering:

- Direct facts and definitions from the source documents
- Concept explanations and comparisons
- Questions requiring evidence from multiple chunks or sections
- Questions with ambiguous wording
- Questions for which the indexed documents do not contain enough evidence, if the application should acknowledge missing information

Manually validate each expected answer against the source document.

### Step 2: Review individual cases

Inspect `evaluation/reports/application_quality_results.json`. For each case, review the question, expected answer, generated answer, retrieved context, each metric's score and reason, duration, and any errors. Pay particular attention to lower scores even when they exceed the threshold.

### Step 3: Validate judge scoring

Keep the judge model and metric criteria fixed while establishing a baseline. Review examples where the score does not match the written reason. If inconsistencies occur, inspect the custom judge adapter and DeepEval score parsing before changing the RAG pipeline.

### Step 4: Check faithfulness against the actual context

Where possible, record the exact chunks supplied to the answer-generation chain and use those chunks for faithfulness and groundedness evaluation. This reduces the risk of evaluating an answer against context different from the context that produced it.

### Step 5: Control rate limits

If HTTP `429` responses become frequent:

- Reduce concurrent judge requests.
- Use bounded retries with exponential backoff.
- Keep the judge model and metric configuration consistent during comparisons.
- Record persistent metric errors explicitly rather than treating missing scores as success.

### Step 6: Track reproducible baselines

For each run, record the dataset version, number of cases, embedding model and FAISS index version, retrieval settings, judge model, metric criteria and thresholds, average scores, pass rates, errors, runtime, and rate-limit events. Use the same dataset and settings when comparing changes.
