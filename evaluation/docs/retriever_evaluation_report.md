# Retriever Evaluation Report

## 1. Overview

This document explains the current retriever evaluation workflow for the
**End-to-End LLMOps Project**, the initial results, what those results
mean, and how to improve retrieval quality.

**Evaluation status:** The evaluation script ran successfully and
generated a JSON report. The results are an initial baseline, not a
final benchmark.

## 2. What Is Being Evaluated?

The retriever is responsible for finding document chunks that are useful
for answering a user's question.

This evaluation checks whether the FAISS retriever returns relevant
context from the indexed source document. It does **not** directly
measure the quality of the final answer generated by the complete RAG
application.

### Components involved

-   **Evaluation dataset:** `evaluation/datasets/retriever_eval.json`
-   **Embedding model:** `sentence-transformers/all-MiniLM-L6-v2`,
    loaded through `ModelLoader`
-   **Vector store:** FAISS
-   **Retrieval strategy:** Maximum Marginal Relevance (MMR)
-   **LLM judge:** Groq model `openai/gpt-oss-120b`, accessed through
    `DeepEvalGroqModel`
-   **Evaluation library:** DeepEval
-   **Evaluation script:** `evaluation/component/evaluate_retriever.py`
-   **Output report:** `evaluation/reports/retriever_eval_results.json`

## 3. Evaluation Workflow

The workflow currently runs as follows:

1.  **Load the evaluation dataset.**\
    The script reads the questions and reference answers from
    `retriever_eval.json`.

2.  **Load the embedding model.**\
    `ModelLoader` loads the configured Hugging Face embedding model. It
    converts text into vectors so semantically similar text can be
    retrieved.

3.  **Load the FAISS index.**\
    The script opens the existing saved index from:
    `faiss_index/session_20261026_215230_88296173`

4.  **Configure the retriever.**\
    The current settings are:

    -   `search_type = "mmr"`
    -   `TOP_K = 3`
    -   `FETCH_K = 10`
    -   `LAMBDA_MULT = 0.5`

    MMR aims to return relevant chunks while reducing excessive
    similarity or redundancy among the selected chunks.

5.  **Retrieve context for each question.**\
    The retriever returns up to three document chunks for each
    evaluation question.

6.  **Create a DeepEval test case.**\
    The question, retrieved chunks, and reference answer are passed to
    DeepEval. In the current script, `expected_output` is also used as
    `actual_output` because the evaluation focuses on retrieval. This is
    a placeholder required by the test-case setup; it is **not** a real
    answer generated by the RAG application.

7.  **Score the retrieved context.**\
    DeepEval asks the configured Groq judge to assess contextual
    precision and contextual recall. The judge returns scores and
    reasons when available.

8.  **Save the report.**\
    Per-question scores and retrieved chunks are written to
    `retriever_eval_results.json`, and average scores are printed in the
    terminal.

## 4. Initial Evaluation Results

Three test cases were evaluated.

  Test case                             Contextual precision   Contextual recall
  ----------------------------------- ---------------------- -------------------
  Transformer architecture                             1.000               1.000
  Self-attention in the Transformer                    1.000               1.000
  Multi-head attention                                 0.333               1.000
  **Average**                              **0.778 (77.8%)**    **1.000 (100%)**

### What does contextual precision mean?

Contextual precision evaluates whether the retrieved chunks are relevant
to the question and how well relevant chunks are ranked. A higher score
generally indicates that relevant context appears more effectively in
the retrieval results.

The average score is **0.778 (77.8%)**. The multi-head attention test
scored **0.333**, which is the main result to investigate. It may
indicate irrelevant chunks, weak ordering, or a judgment issue. Inspect
the actual retrieved chunks before deciding which explanation is
correct.

### What does contextual recall mean?

Contextual recall evaluates how much of the information needed to
support the reference answer is present in the retrieved context.

The average score is **1.000 (100%)** across these three test cases. The
judge considered the retrieved context sufficient for the reference
answers in this small dataset. This does not prove that retrieval is
perfect for all questions.

## 5. What Is Working and What Needs Attention?

### Working

-   The evaluation script completes and saves a report.
-   The embedding model and FAISS index load successfully.
-   Both DeepEval metrics return scores.
-   The retrieved context is available in the JSON report for
    inspection.
-   The initial results provide a baseline for future changes.

### Needs attention

-   The dataset contains only three questions, so the results are not
    representative enough for a reliable benchmark.
-   The multi-head attention precision score is low and needs
    investigation.
-   The current test case uses the reference answer as `actual_output`.
    Therefore, this is a **retrieval-focused evaluation**, not an
    end-to-end answer-quality evaluation.
-   The LLM judge can be inconsistent or incorrect. Its scores should be
    checked against the source document and manually reviewed examples.
-   Groq returned HTTP 429 rate-limit responses during the run, although
    retries succeeded. Larger evaluations may need rate limiting or
    controlled retry/backoff handling.
-   The initial reference answers and expected facts should be checked
    against the original source PDF before being treated as
    gold-standard labels.

## 6. How to Improve the Retriever

Make one change at a time and rerun the same dataset so that results can
be compared fairly.

### Step 1: Inspect the low-scoring case

Start with `retriever_003`:

> Why does the Transformer use multi-head attention?

Open `evaluation/reports/retriever_eval_results.json` and inspect its
`retrieved_context` entries. Check:

-   Does each chunk discuss multi-head attention?
-   Is the most useful chunk ranked first?
-   Are any chunks unrelated or repetitive?
-   Are chunks incomplete fragments that omit important context?

Do not change retriever settings until the retrieved chunks have been
inspected.

### Step 2: Improve the evaluation dataset

Increase the number and diversity of test cases. Include questions
about:

-   Direct facts stated in the document
-   Definitions and explanations
-   Comparisons between concepts
-   Questions requiring evidence from multiple sections
-   Questions for which the index should not return relevant evidence,
    if the application is expected to handle such cases

For each case, keep the question, reference answer, and expected facts
grounded in the source document. Review the expected facts manually.

### Step 3: Establish a baseline and track changes

Keep a copy of the initial report before changing configuration. Record:

-   Embedding model
-   Chunk size and overlap used when building the index
-   Retrieval strategy and its parameters
-   Number of retrieved chunks (`top_k`)
-   Evaluation dataset version
-   Judge model
-   Precision and recall scores
-   Any errors or failed test cases

This makes comparisons reproducible and helps explain improvements in an
interview.

### Step 4: Experiment with retrieval settings

After inspecting the current chunks, test one parameter at a time:

-   **`TOP_K`:** Try a small set of alternatives, such as 3, 5, and 8.
    More chunks may improve coverage but can add irrelevant context.
-   **`FETCH_K`:** Test a larger candidate pool for MMR, for example 10,
    20, or 30, if the index size supports it.
-   **`LAMBDA_MULT`:** Compare values such as 0.25, 0.5, and 0.75. Lower
    values generally emphasize diversity more; higher values generally
    emphasize similarity more.
-   **Search strategy:** Compare MMR with ordinary similarity search
    using the same questions and scoring method.

These are experiments, not guaranteed improvements. Choose settings
based on consistent results across the larger dataset, not a single
question.

### Step 5: Investigate chunking and embeddings

If retrieved text is consistently incomplete or misses the needed
evidence:

-   Review the chunk size and overlap used during ingestion.
-   Check whether headings, paragraphs, tables, and page boundaries are
    preserved appropriately.
-   Compare embedding models on the same evaluation dataset.
-   Rebuild the FAISS index after changing chunking or embeddings. Do
    not evaluate a new embedding model against an index created using
    incompatible embeddings.

### Step 6: Add reranking if needed

If the initial retrieval returns useful chunks but ranks them poorly,
test a reranker (for example, a cross-encoder) on the candidate chunks.
Compare the reranked results against the baseline using the same dataset
and metrics.

A reranker adds computation and latency, so retain it only if the
quality improvement justifies the cost.

### Step 7: Handle judge rate limits

If HTTP 429 responses become frequent:

-   Reduce concurrent evaluation requests.
-   Add bounded exponential backoff and retry handling.
-   Keep the judge model and evaluation settings fixed when comparing
    experiments.
-   Record failed evaluations rather than silently treating missing
    scores as zero or success.

## 7. Recommended Improvement Order

1.  Inspect the chunks for `retriever_003`.
2.  Verify the three reference answers and expected facts against the
    source PDF.
3.  Expand the dataset to a more representative set of questions.
4.  Save the current results as the baseline.
5.  Test `top_k`, `fetch_k`, and `lambda_mult` one at a time.
6.  Compare similarity search and MMR.
7.  Investigate chunking and embedding alternatives if necessary.
8.  Test reranking if ranking remains a problem.
9.  Rerun the full dataset and compare the results.
10. Add the final results and methodology to the project's evaluation
    documentation.

## 8. How to Run the Evaluation

From the project root, run:

``` powershell
uv run python -m evaluation.component.evaluate_retriever
```

The script should load the configured embeddings and FAISS index,
evaluate each question, print scores, and write the JSON report to:

``` text
evaluation/reports/retriever_eval_results.json
```

The current script references a specific session index directory. If a
new index is created, update `INDEX_PATH` or refactor the script to load
the intended index through configuration.

## 10. Final Takeaway

The evaluation pipeline is **operational**, and the first baseline has
been recorded. The most important next action is to investigate the low
contextual precision score and strengthen the evaluation dataset. A high
recall score is encouraging, but the small sample size and LLM-judge
nature of the metrics mean the results should be treated as preliminary.
